# Benchmarks against other batch renderers

This directory measures neraulgraphics against the batch renderers that sit next to a simulator, and only calls a result when the
comparison was fair. Today that is MuJoCo Warp 4.0.0 (with MuJoCo 4.0.0 and Warp 1.19.0). Newton and ManiSkill come next.

## The rules

1. **Every competitor is the latest stable release**, pinned exactly in `envs/*.lock.txt`, in an environment of its own. Nothing
   here is a dependency of the package.
2. **Identical work or no claim.** A case is compared only when both renderers were handed the same triangles, the same
   poses, the same camera and the same image size, were set to do the same rays per pixel, and drew the same picture (checked, below).
3. **One claim per case.** A result says "faster at 1,024 worlds of 64x64 with 8 bodies each", never "faster".
4. **Preconditions are enforced by the code.** `analyze.py` prints `NO CLAIM` if the pose hashes differ or the pictures disagree.

## Reproduce

```bash
uv venv --python 3.12 ~/bench-competitors && uv pip install --python ~/bench-competitors/bin/python -r bench/envs/competitors.lock.txt
uv venv --python 3.12 ~/bench-ours        && uv pip install --python ~/bench-ours/bin/python        -r bench/envs/ours.lock.txt
bench/run_all.sh ~/bench-competitors/bin/python ~/bench-ours/bin/python 5 bench/results/run1
```

The ours environment is `pip install neraulgraphics` (the released wheel, not a source build) plus the Warp and MuJoCo the
adapter uses. Leave the GPU alone while it runs: about half an hour. The recorded poses (`data/`) and the verification images
(`results/*/verify_*.npz`) are regenerated by `run_all.sh` and are not tracked.

## What is held equal

| | MuJoCo Warp | neraulgraphics |
|---|---|---|
| Geometry | the same ball (320 triangles) and box (12) meshes, as MJCF `<mesh>` assets | the same meshes, through `MJWarpBatchRenderer` |
| Poses | recorded once from MuJoCo Warp physics, replayed | the same arrays, same hash |
| Camera | `<camera>` in the model, 45 degree vertical field of view | the same matrix, a device array, same field of view |
| Rays per pixel | 1 primary (`samples_per_pixel=1`) | 1 primary (`samples_per_pixel=1`) |
| Shadows | `use_shadows=True`, one light | one light with `radius=0`, a hard shadow |
| Bounces | none | none (`reflectivity=0`) |
| Textures | `use_textures=False` | none |
| Output | RGB only | RGB only |
| Resolution, worlds, bodies | identical | identical |

## What is not equal (disclosed, not hidden)

- **Shading arithmetic differs.** MuJoCo Warp evaluates a Blinn-Phong style model with a headlight and ambient terms; neraulgraphics
  evaluates Phong with a constant ambient and converts to sRGB. The pictures differ in colour. Both cost a few arithmetic
  operations per hit, but that is not zero and it is not identical.
- **The light is a directional light in one and a point light in the other.** Each costs one shadow ray per lit pixel.
- **Missed rays**: MuJoCo Warp writes a constant background; neraulgraphics evaluates its sky.
- **Output format**: MuJoCo Warp renders to a packed 32-bit pixel, neraulgraphics to 3 bytes. The `unpacked` boundary charges MuJoCo
  Warp for converting to float RGB; the `native` boundary does not.
- **Hand-off of poses**: neraulgraphics composes geom poses into instance matrices and rebuilds its instance trees; MuJoCo Warp
  refits its BVH. Both are inside the timer, because each is what that renderer needs before drawing a moved scene.

## The picture check

`run_*.py --verify` renders 16 worlds at 128x128, in two frames (one at rest, one with bodies moving), and saves depth. A miss is
`0` in MuJoCo Warp and infinity here, so the check compares silhouettes (intersection over union) and, on shared pixels, depth.
The thresholds are in `analyze.py`.

## Method

Each case is 30 repetitions of a block of frames, each timed between two device syncs, after at least 1.5 s of warmup. The block
length is chosen so a repetition lasts about 50 ms. The whole set is run for several rounds with the order of the two systems
alternating, so slow drift (temperature, clocks, background load) lands on both. A verdict needs the bootstrap interval of the
ratio of medians to exclude 1 **and** every round to point the same way. The interval resamples back-to-back repetitions and is
therefore optimistic; the spread across rounds is the better measure of repeatability.

## Results (run2: neraulgraphics 0.5.0 against MuJoCo Warp 4.0.0, RTX 5090, 5 rounds, 24 cases)

Full table: `results/run2/summary.txt`. Both systems replayed identical poses (same hash) and drew the same picture (silhouette IoU
at least 0.99985, depth within 0.002 mm at the 99th percentile) in every scene.

- **Against MuJoCo Warp's default configuration** (the matched-work one): neraulgraphics is faster in 21 of 24 cases, by 1.1x to
  4.4x, and slower in 3 (the smallest batches: 0.75x to 0.97x).
- **Against MuJoCo Warp's fastest configuration** (switching off specular, emission, per-light ambient, backface culling and vertex
  normals, which does less work than neraulgraphics does): faster in 18 of 24, by 1.05x to 2.6x, and slower in 6, all at 1,048,576
  pixels per frame or fewer (0.69x to 0.97x).
- The speedup grows with the work per frame (Spearman 0.95 between pixels per frame and speedup, speedup roughly proportional to
  pixels^0.19); the crossover against the fastest configuration is near 0.4 million pixels per frame.
- Nsight Systems agrees with the timer: 4.30 ms of GPU kernel time per frame against 4.03 ms measured, at 4096 worlds of 128x128.
  In both renderers one kernel is nearly the whole frame; pose updates and acceleration-structure work are about 1%.
- MuJoCo Warp's render kernel cannot launch at block sizes of 512 or more on this GPU. Block size 256 helped in some cases and not
  others, within the run-to-run noise of the sweep, which is why it is a variant and not an assumption.

## Limits of what this establishes

- One machine, one GPU (RTX 5090), one driver. Another GPU can rank these differently.
- Render-only: physics is not in the timer. How much a faster renderer helps an end-to-end training loop depends on how much of
  the step the renderer is; in a first baseline, physics was most of a frame.
- Two scenes (8 and 32 small bodies per world). Scenes with large meshes or many lights are not measured.
- GPU clocks are not locked (that needs root). Each case records the clock, temperature and power before and after.
